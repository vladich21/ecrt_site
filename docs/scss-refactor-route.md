# Маршрут рефакторинга стилей (очистка и упорядочивание)

Документ задаёт **порядок работ по страницам и фичам**, чтобы каждый шаг имел понятный scope, ограниченный риск регрессий и повторяемый чек‑лист. Совместимо с общими принципами в [`scss-conventions.md`](./scss-conventions.md).

**Релизная единица:** один пункт маршрута = один последовательный PR (или отдельный коммит внутри ветки), не смешиваем несколько больших блоков без причины.

---

## Принцип порядка (зачем так)

1. **Сначала «изолированные» страницы** (purchase, careers): один файл стилей, мало связей — быстрее задаём ритм и стиль правок без ломания остальных маршрутов.
2. **Затем пары shell + содержание** (documents, contacts, блоки about/home): уже видно паттерны повторного использования `SitePageShell` и можно решать, какие именно классы «принадлежат» какому экрану.
3. **Потом составные домены** (projects, project detail): несколько связанных SCSS модулей; чистить вместе контролируемо (unused, дубликаты между витриной и accordion).
4. **Главная** — когда руки набиты: много секций за один проход, но уже есть единые договорённости.
5. **`site-page-shell` отдельно** — когда собран grep по четырём потребителям (`HomePageClient`, `ContactsPageView`, `DocumentsPageView`, `AboutChronologySection`) и ясно, что разрезать или что оставить одним файлом с внутренними секционными комментариями.
6. **Layout (header/footer/…) в конце** — одно изменение касается всех страниц сразу; туда переходят после стабилизации фич.

---

## Чек‑лист на каждый шаг (повторять дословно)

Выполнение по пунктам снижает шанс «почистил и что-то пропало визуально».

1. **Зафиксировать scope.** Один элемент таблицы выше → список `*.module.scss` и TSX только для этого scope.
2. **Сопоставление классов.**  
   - Для каждого импорта `styles` / `shellStyles` / `siteStyles` — полный grep по файлу вида `\b(styles\.)` и шаблоны `styles[\`…\`]`.  
   - Помечать в SCSS блоки без ссылок в JSX как кандидатов на удаление (перепроверить вложенные классы и `classNames` сборки строк).
3. **Дубликаты без смысла.** Два блока с почти одинаковыми `margin/font-size/color` — либо один класс-паттерн в том же модуле с комментарием «общий паттерн для …», либо минимальный `@mixin` **в этом же файле**, если явно переиспользуется дважды стабильно.
4. **Специфичность.** Убрать `!important` там, где решается селектором (исключение: осознанные a11y-оверрайды — см. конвенцию).
5. **Вложенность.** Цель по глубине: не глубже 2 осмысленных уровня для произвольных блоков (исключение: псевдоэлементы, `@media`).
6. **Локальный аудит.** `npm run audit:css-modules` — читать вывод как **подсказку**, не как вердикт.
7. **Сборка.** `npm run build` обязательно.
8. **Дым по маршрутам.** Открыть RU URL и соответствующий EN для этого scope; ключевые вьюпорт 360 / 768 / 1200 если блок отзывчивый.

**Definition of done для пункта маршрута:** чек‑лист пройден, build зелёный, нет необоснованных правок «заодно» в других фичах.

---

## Откат и безопасность

- Править в рамках **одной фазы**; смежные улучшения — отдельный пункт маршрута.
- Если сомнение «используется ли класс»: временно добавить временный маркер в комментарий SCSS `// REVIEW_RM` или не удалять, а пометить в PR для второго пара глаз.
- После фазы с `SitePageShell` — обязательно прогон дым-тестов по всем четырём потребителям, перечисленным в таблице.

---

## Как использовать этот план в работе с ассистентом

На каждый следующий пункт маршрута формулируй запрос узко: *«Фаза 3, только `about-page.module.scss` + секции без таймлайна»* или *«Фаза 7, только классы домашней секции hero в `site-page-shell` после grep»*. Тогда правки получаются **детализированными** и воспроизводимыми, как техническая задача из внутренней документации команды.

## Дальнейшее уплотнение (не блокирует очистку)

- Вынести токены в [`app/globals.css`](../app/globals.css) или один `src/styles/_tokens.scss` — **отдельная** задача после 1–2 фаз очистки, когда видны повторы цветов/радиусов.
- Выделить маленький `animations.scss`/partial для `@keyframes`, общих для нескольких фич — только если один и тот же keyframes реально нужен минимум в двух feature-модулях.
